# Architecture

A single-module Android app (`app/`, package `com.iron.breakfast`): Kotlin, Jetpack Compose, Material 3, Room. There is no DI framework, no navigation library and no repository layer; this is deliberate for a one-person, local-only app. Read `PRODUCT.md` for product rules and `DESIGN.md` for the locked Monochrome design.

## Package map

## State owners

All state lives in `BreakfastViewModel` and the owners it builds (`DiarySession`, `Notices`, `SettingsState`, `UndoController`, `MatchFeedback`, `ContributionFlow`, `OffSearch`, `DiaryTransfer`, `ExportReminders`, `ScanSession`, `ProductReview`, `FoodForm`, `EntryEdit`, `LogComposer`, `LibraryState`, `ResolveFlow`, `Surfaces`), so it survives configuration changes (the app is portrait only; dark mode and font size still recreate the activity); very little survives process death.

`DiarySession` (`app/DiarySession.kt`, built by the VM with a `DiarySource` over `BreakfastEngine`, `viewModelScope` and two callbacks) owns the diary as shown and the one way to write it:

- **Read model:** `foods`, `entries`, `ready` and `storageUnavailable`. `refresh()` reloads them (and reloads a stale snapshot once more); `open()` opens storage and is also the storage dialog's Try again.
- **Write gate:** `busy`, one diary write at a time (a UX rule over the store's own lock). Every user write goes through `write(change, nonCancellable, onFailure, onSuccess) { run }`, where `change` is either a `DiaryChange` or a function of what `run` returned. It is refused unless storage is open and nothing runs, and holds the gate from the call. `nonCancellable` (the full entry edit) finishes the write and its handlers even if its job is cancelled. Without `onFailure` a failure propagates; a cancel is never a failure. Work that only needs the diary to stand still (Export diary, reading an import file: picker results that can arrive before storage is open or while a write runs) goes through `whenIdle(onSuccess) { run }`, which waits until both are true, holds the gate and publishes nothing.
- **Fan-out:** after `run` returns, `change` names the committed `DiaryChange` (`app/DiaryChange.kt`), or null when nothing was committed (a refused edit). A write that committed rows always names one, even when its screen is gone: an entry edit saved after its edit closed is `EntryEditedAfterClose` (reloads, keeps Undo), and a "Not right?" pick whose learning failed is still `MatchCorrected`. The session reloads the read model (unless the change has no rows, a confirmed match), publishes the change to its listeners, then runs `onSuccess`. The VM registers three listeners, in order: `UndoController` (`undoAfterChange`), `MatchFeedback` (a logged batch opens feedback, a diary replace ends it) and the Library list (recomputed for changes with `refreshesLibrary`). Features never set `busy`, call `refresh`, refresh the Library or end Undo after a write themselves.

`Surfaces` (`app/Surfaces.kt`) is the one place that knows what is open and in which order. Each owner keeps its own open state (the Log page, the scanner, the resolver, a dialog's flag); `shown()` derives from it the ordered list of `Surface`s drawn now. The `Surface` declaration order is the drawing order (the base screen, Daily, Meal or Library, first); the scanner and the entry detail are drawn alone (not even a notice until they close); the scan review's backdrop replaces the base, the Log and the resolver, which wait undrawn; "No local match" joins only with nothing over the Library. From that one list come:

- **Drawing:** `IronApp` draws `shown()` bottom first (with the ghosts of screens gliding out, which are not open; see Motion).
- **Back:** `back()` runs the Back of the topmost surface that takes it (the same action as its arrow: `scan.end`, `foodForm.leave`, `settingsBack`, `exitLibrary`, ...); a dialog or sheet takes Back in its own window first. The base takes Back only when nothing covers it (`Surface.coversBase`), and Daily never (the system goes back). Back on the contribution sign-in closes it, also while it submits: the submit is cancelled and its answer ignored (`ContributionFlow.dismissAuth`).
- **The top check:** `baseCovered()`, a surface with `coversBase` drawn: "No local match" and the export reminder stay hidden while one is.


Legitimate stacking stays: the scanner over the food form (Back returns to the form as it was), the resolver under the search, the food form and product review (it comes back when one closes without resolving, and waits under a scan backdrop), the resolver after a background save, the Log and Library part frame with its children, Settings and its pages over the Library, the entry detail and its edits over their meal, the contribution screens, dialogs and notices. `SurfacesTest` pins each case over every owner wired as the VM wires them (`AppKit`). Contradictions the old flags allowed are now unrepresentable (drawing, Back and the top check disagreeing: one list feeds all three) or impossible through the operations of `Surfaces` (the search, the food form and the resolver replace each other; every way out of the Library closes Settings; opening the Library clears `meal`).

`Notices` (`app/Notices.kt`) is the app's one modal message: diary results, Open Food Facts and scanner outcomes, refused input. It is app-level rather than the diary's, because most messages are not about a diary write. The VM builds one and the features show through it; the root draws it. It is state, not an event: it stays until dismissed (so a recreation draws it again), and a new message replaces the one showing.

## Motion

The Quiet motion (DESIGN.md, Motion) has one rule, in `ui/components/Motion.kt`: `rememberMotion()` gives the specs and transitions, and with reduced motion (`rememberMotionReduced`: Motion is Reduced, or the phone's animations are removed) every spec is `snap()` and every transition none. Nothing else decides whether something moves.

- **Screens:** `SurfaceTransitions` only remembers what was drawn last; `Surfaces` stays the one model of what is open. A gliding screen (`Surface.glides`: the full screens in the app's window) fades and rises in. It and the base are recorded as they draw, so when one closes it can be drawn for a moment as a picture of its last frame (a `Ghost`): no composition, no touch, no TalkBack, and Back already acts on the new top. The base stays as a still picture under the entry detail while the detail comes in (the detail is drawn alone). The scanner comes and goes without motion. On API 28 the picture cannot keep its layers, so screens there close at once.
- **Lists:** lazy lists (Meal, Library) use `Modifier.animateItem` with `Motion.listItem()`; a removed row is a picture there too. The other lists (Daily's meals, the Log's rows) use `AnimatedRows`, which keeps a removed row where it was, `inert`, until it has collapsed; a new day shows its rows at once.
- **Feedback:** `Reveal` shows the Undo snackbars and "Not right?"; while one leaves it is `inert`. The Undo and feedback timing are the owners' (`UndoController`, `MatchFeedback`), unchanged by the motion.

## Durable save path

Add (or any edit) runs in `viewModelScope` through `DiarySession.write`: `BreakfastViewModel` calls `BreakfastEngine` (for example `save`, `saveCustomAndLog`, `replaceEntry*`), which calls a `BreakfastStore` suspend function. The store takes one `Mutex`, switches to `Dispatchers.IO` under `NonCancellable` (every user-confirmed write; a cancel while waiting for the lock writes nothing), writes inside `database.withTransaction`, then reloads the whole `StoreSnapshot`. The gate runs these calls in `suspendRunCatching`, which rethrows `CancellationException`, so a cancel is never shown as a failed save. "Saved" means that Room transaction committed. If the reload after it fails, the write still counts as saved: the snapshot is marked stale and reloaded on the next refresh, so a retry never logs the same food twice. Entry edits re-read the row inside the transaction and write it with `UPDATE ... WHERE id`, so a deleted entry is never re-created; saving an edited food keeps its stored archived state. A logged entry stores its own nutrition snapshot and conversion provenance, so later food edits never rewrite history. Migrations are additive and there is no destructive fallback.

## Export and import

Settings has Export diary and Import diary. Both use the system document picker (Storage Access Framework), so no permission is needed. The pickers are registered in `IronApp`, which is always composed, so a result that arrives after the activity was recreated still reaches the VM; it waits until storage is open and no write is running. The import picker offers `application/json`, `application/octet-stream` and `text/plain` (files from file managers, messengers and email). Export says "Diary exported." only after the file was checked, written, read back identical and parsed as an import would; on any failure the created document is deleted and "Could not export the diary." shows, so no empty or partial file is left looking like a backup. The file is one JSON document (`data/DiaryExport.kt`, kotlinx-serialization, strict: unknown or missing fields fail):

- `format` (`"breakfast-diary"`), `formatVersion` (1: the layout of this file), `schemaVersion` (the Room schema the rows came from, now 6), `exportedAtEpochMs`.
- `settings`: `dayStartHour` and `longDraft` (a `LongDraft` name).
- One array per Room table, every row and column as stored: `foods` (`foods`: bundled catalogue rows, custom, Open Food Facts, archived and personally edited foods), `foodAliases` (`food_aliases`), `servingConversions` (`serving_conversions`), `preferences` (`preferences`), `mealEntries` (`meal_entries`, each with its own nutrition snapshot). Rows are sorted by key, so the same diary always writes the same file. An alias, conversion or preference whose food is not stored is left out (the app never shows one).

Catalogue rows are included as stored rather than re-derived, so a built-in food the user edited or archived comes back exactly. Import reads the whole file (at most 32 MB) and checks all of it before anything is written: the format and its version, a schema version no newer than the app's, settings in range, every enum name known, every number finite and not negative (a nutrition basis and a serving size above zero), day keys real dates, ids unique (per table key), and each alias, conversion and preference naming a food in the file. An entry's food id need not name a food: the entry keeps its own name and snapshot. A file that fails any check changes nothing and shows "That file can't be imported."; the reason goes to logcat (tag `Breakfast`). A file that passes asks, in a dialog with one line ("This replaces entries and foods, not settings."), Cancel or Replace diary. Replace diary first writes the current diary, in the same format, to the safety copy `no_backup/diary-before-import.json` (see Recovery); if that fails, nothing is replaced and "That file can't be imported." shows. It then runs `BreakfastStore.replaceDiary`: one Room transaction deletes every table, inserts the file's rows (a clash aborts), then seeds and syncs the catalogue as at start, so a file from an older build gets the current catalogue. A failure rolls everything back. The settings in the file are checked but never applied: day start and long draft stay as they are on the phone. The session is reset as after Delete all (see State owners, `SessionReset`): Undo, "Not right?" feedback, log pins, a contribution candidate, the resolve queue and the entry detail from the old diary are dropped. `DiaryImportTest` (androidTest) covers export, wipe, import with equal counts and checksum, and a failing insert that leaves the previous diary.

Settings, Data has two more switches and an action. **Safety copy** Keep (default) is the behaviour above; Don't keep writes no copy before Replace diary and deletes an existing one (also at once when chosen). **Export reminder** Weekly or Monthly shows "Export your diary." with Export on Daily when 7 or 30 days have passed since the latest of the last successful export (`last_export_ms`), the last time it was on screen (`export_reminder_shown_ms`) and the moment it was turned on from Never (`export_reminder_enabled_ms`), so the first one comes one interval after turning it on. It is drawn only on Daily itself (not while the Log page or any screen or sheet covers it: `Surfaces.baseCovered`) and counts as shown only once drawn. **Delete all data** opens a dialog ("This deletes all entries and foods.", the chip "Also settings and learned picks", off, then Cancel or Delete all). Delete all always writes the safety copy first, whatever Safety copy says (no copy, no delete), then runs `BreakfastStore.deleteAllData`: one Room transaction deletes every entry, food, alias and conversion and seeds and syncs the catalogue as at a first start; with the chip it also deletes the preferences, and every setting is cleared to its default. A failure rolls everything back and shows "Could not delete the diary." (`BreakfastStoreTest`, androidTest).

When the schema changes, bump `DIARY_SCHEMA_VERSION` with it (a unit test fails until it matches `app/schemas` and covers every table), and keep reading files from older schema versions.

## Day boundary

A diary day starts at the "Day starts at" hour (Settings, 00:00 to 23:00, default 00:00). `dayKeyFor(epochMs, zone, dayStartHour)` gives the day an instant belongs to: before the start hour it is still the previous date, read from the wall clock so a daylight-saving day is one day. It decides what "today" is (`todayKey`: the Daily header and Today button, Next, the date picker's last day) and so the day a new log lands on, since every log goes to the selected day. Stored entries keep their stored `dayKey`; changing the setting rewrites nothing. `resolveSelectedDay` (in `AppDecisions.kt`) moves the selection only on a return: when the activity starts again after a stop, or the VM is created or restored, a user following today lands on the new today and a picked past day stays. While the app is on screen the selection never moves; the 60-second loop only recomputes `todayKey`, so after the day turns the old day shows with the Today button, as after a swipe. Changing the setting counts as a return.

## OFF boundary

`OpenFoodFactsClient` uses `HttpURLConnection`, HTTPS only, 4.5 s timeouts, off the main thread. It is called only on an explicit action: submitted search (`cgi/search.pl`, then `search.openfoodfacts.org`), barcode lookup (`api/v3/product`), and the optional contribution from food detail (`cgi/session.pl` login, then `cgi/product_jqm2.pl`). There is no search-as-you-type and no automatic retry of writes. Search and barcode lookup are suspend functions: a new query or leaving the scanner cancels them, which disconnects the request in flight and skips the fallback search. Preflight and contribution run to the end. Only a transport failure (`IOException`) is "no connection"; an HTTP error other than 404 or an unreadable body is a server error. A contribution whose answer is lost after its body was written is reported as possibly sent, and Retry reads the product again before anything is resent. Data read from and sent to OFF passes one plausibility rule, `plausibleNutrition` (per 100 g or ml: kcal 0 to 1000, macros 0 to 100 g). The User-Agent is `Breakfast/<versionName> (daily food logger)`, from `BuildConfig.VERSION_NAME`. The OFF password is held in VM memory only, cleared when the submit starts, and **never persisted** (not to Room, not to `SavedStateHandle`). Core logging works offline.

## Signing

Every build, including `perf`, is signed with the machine's Android debug key, `%USERPROFILE%\.android\debug.keystore` (SHA-256 `98:93:7B:8D:95:25:A4:58:E1:71:55:F7:67:DB:0F:6A:26:09:3D:4A:23:74:7C:11:6E:D6:E4:5D:4B:AE:4B:1D`). **Back this file up.** A build signed with a different key cannot be installed over the current one: Android forces an uninstall first, and the uninstall deletes the diary.

Decided 2026-10-26 (P10): this key stays the permanent signing key, and the owner keeps a copy off this machine. There is no separate debug `applicationId`, so debug and perf share `com.iron.breakfast` and `breakfast.db`. The recovery path for the diary is Export diary: if the key is ever lost or replaced, export the diary first (or use the latest exported file), uninstall, install the new build, then Import diary and Replace diary.

## Backup

`android:allowBackup="true"` with explicit rules (MOB-012, decided 2026-10-26: the diary stays out of Google's cloud):

| Copy | Android 12+ (`res/xml/data_extraction_rules.xml`) | Android 11 and older (`res/xml/backup_rules.xml`) |
| --- | --- | --- |
| Google cloud backup | Settings (`SharedPreferences`) only. `breakfast.db` and its `-wal`, `-shm` and `-journal` files are excluded. | The same: the database files are excluded. |
| Device-to-device transfer (cable or local transfer to a new phone, such as Smart Switch) | Everything, the diary included (no device-transfer rules, so all app data moves). | Not the diary: one rule set covers both, and it excludes the database. |

The backup is the user's own file: Settings, Export diary (see Export and import). After a reinstall or on a new phone, Import diary puts it back.

## Recovery and testing on the phone

- Safety copy: every Replace diary (unless Settings, Safety copy is Don't keep) and every Delete all data first saves the diary as it was to `/data/user/0/com.iron.breakfast/no_backup/diary-before-import.json` (`noBackupFilesDir`; only the latest, written to a temp file and renamed). It is never backed up and has no UI. On the non-debuggable perf build it cannot be read without root. To get it: install the debug build over perf (`adb install -r app-debug.apk`, same key and data), then `adb exec-out run-as com.iron.breakfast cat no_backup/diary-before-import.json > diary-before-import.json`, then put perf back. That file can be imported with Import diary.
- Update in place only: `adb install -r app/build/outputs/apk/perf/app-perf.apk`. `-r` keeps the app's data. Never uninstall; never install a build signed with another key.
- **Never run `connectedDebugAndroidTest` against the owner's phone.** AGP uninstalls the app under test afterwards, and `debug` shares the `com.iron.breakfast` applicationId with `perf`, so it would wipe the diary.
- Safe manual run of the instrumented tests (`BreakfastDatabaseTest`; it uses its own throwaway databases):

  ```powershell
  .\gradlew.bat assembleDebug assembleDebugAndroidTest
  adb install -r app/build/outputs/apk/debug/app-debug.apk
  adb install -r app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
  adb shell am instrument -w com.iron.breakfast.test/androidx.test.runner.AndroidJUnitRunner
  adb install -r app/build/outputs/apk/perf/app-perf.apk
  ```

  The last step puts the perf build back. The test APK (`com.iron.breakfast.test`) can stay installed or be removed with `adb uninstall com.iron.breakfast.test`; that never touches the app's data.
- If storage fails to open, the app shows "Storage unavailable" with Try again, which runs the same open once more (`openStorage` in `AppDecisions.kt`); the cause goes to logcat (tag `Breakfast`), not to the screen. The database file is untouched.
